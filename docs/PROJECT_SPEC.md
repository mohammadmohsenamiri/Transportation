# مشخصات محصول و نیازمندی‌ها

## 1. هدف

ساخت سامانه تحت وب فارسی برای برنامه‌ریزی و پایش حمل بار در شبکه داخلی. سامانه باید امکان تعریف ساختار دفاتر، انبارها، خودروها، مرسوله‌ها، مسیرها و مأموریت‌ها را فراهم کند و بدون GPS واقعی، موقعیت تقریبی خودرو را بر مبنای زمان، سرعت و مسیر محاسبه و روی نقشه نمایش دهد.

## 2. اصطلاحات دامنه

- **مرسوله (Shipment):** واحد بار دارای کد رهگیری، نوع بار، مبدأ و مقصد.
- **مأموریت (Mission):** برنامه حرکت یک خودرو از یک انبار به یک مقصد در زمان مشخص برای حمل یک یا چند مرسوله.
- **مسیر (Route):** فهرست مرتب نقاط جغرافیایی قابل استفاده مجدد در مأموریت‌ها.
- **موقعیت تقریبی:** خروجی محاسباتی و نه داده واقعی GPS.
- **زمان مشاهده (View Time):** زمانی که نقشه برای آن وضعیت مأموریت‌ها را بازسازی می‌کند؛ می‌تواند اکنون یا زمان انتخاب‌شده روی سیکر باشد.
- **فرانمای وضعیت:** داشبورد سطح کلان سامانه.

## 3. نقش‌ها

نقش‌ها به‌صورت many-to-many به کاربر تخصیص داده می‌شوند تا یک کاربر بتواند بیش از یک نقش داشته باشد.

### `MISSION_PLANNER` — برنامه‌ریز مأموریت

- مشاهده داده‌های مرجع لازم برای برنامه‌ریزی
- ایجاد و ویرایش پیش‌نویس مرسوله و مأموریت
- انتخاب خودروهای آماده و بدون تداخل زمانی
- انتخاب یا ترسیم مسیر و import CSV
- انتشار، لغو یا تکثیر مأموریتی که مجوز آن را دارد
- مشاهده نتیجه ثبت و اعتبارسنجی؛ بدون دسترسی به مدیریت کاربران و تنظیمات زیرساختی

### `STATUS_VIEWER` — بیننده وضعیت/مدیر

- مشاهده فرانمای وضعیت، نقشه، جدول مأموریت‌ها، فیلترها و جزئیات
- تغییر زمان مشاهده روی سیکر
- export گزارش‌های مجاز
- عدم امکان تغییر داده‌های مرجع یا ثبت/ویرایش مأموریت مگر نقش دیگری نیز داشته باشد

### `ADMIN` — مدیر سامانه

- تمام مجوزهای دو نقش دیگر
- مدیریت کاربران و نقش‌ها
- مدیریت سلسله‌مراتب سازمانی، خودروها، انواع خودرو، انواع بار، Provider نقشه و آیکن‌ها
- درون‌ریزی سبک نقشه از فایل Mapnik Style (XML) برای تولید Provider داخلی جدید (پیشنهادی، هنوز پیاده نشده — ADR-022)
- مشاهده audit log و وضعیت سلامت سامانه
- اعمال تنظیمات منطقه زمانی، محدودیت فایل و سیاست‌های امنیتی

### ماتریس حداقل مجوز

| قابلیت | Planner | Viewer | Admin |
|---|---:|---:|---:|
| مشاهده داشبورد و نقشه | ✓ | ✓ | ✓ |
| ایجاد/ویرایش مرسوله | ✓ | — | ✓ |
| ایجاد/ویرایش/لغو مأموریت | ✓ | — | ✓ |
| مدیریت مسیرها | ✓ | مشاهده | ✓ |
| مدیریت ساختار دفاتر و انبارها | — | مشاهده | ✓ |
| مدیریت خودرو و نوع خودرو | — | مشاهده | ✓ |
| مدیریت کاربران، نقش‌ها و Provider | — | — | ✓ |
| مشاهده audit log | — | — | ✓ |

تمام مجوزها باید در server enforce شوند. در صورت اضافه شدن scope سازمانی، مدل `UserOrganizationScope` بدون تغییر بنیادی در RBAC قابل فعال‌سازی باشد.

## 4. ساختار سازمانی چهارسطحی

سامانه دقیقاً این سطوح را پشتیبانی می‌کند:

1. `COUNTRY_OFFICE` — دفتر کشوری؛ parent ندارد.
2. `GROUP_OFFICE` — دفتر گروه؛ parent باید دفتر کشوری باشد.
3. `DISTRIBUTOR_OFFICE` — دفتر توزیع‌کننده؛ parent باید دفتر گروه باشد.
4. `WAREHOUSE` — انبار؛ parent باید دفتر توزیع‌کننده باشد.

قواعد:

- نام، کد و وضعیت فعال برای هر گره الزامی است.
- طول و عرض جغرافیایی برای نمایش روی نقشه الزامی است؛ برای ایجاد اولیه می‌توان رکورد را draft نگه داشت تا مختصات تکمیل شود.
- جابه‌جایی گره فقط به parent معتبر مجاز است و نباید cycle بسازد.
- حذف گره دارای فرزند، مأموریت یا مرسوله ممنوع؛ فقط غیرفعال‌سازی/soft delete.
- آیکن هر گره قابل انتخاب از کتابخانه assetهای تأییدشده است.

## 5. خودرو و انواع خودرو

### VehicleType

- توسط Admin تعریف می‌شود و هیچ مقدار business پیش‌فرضی وجود ندارد.
- فیلدها: نام، کد اختیاری، توضیح، آیکن، وضعیت فعال.
- نوع استفاده‌شده در خودرو قابل حذف فیزیکی نیست.

### Vehicle

فیلدهای الزامی:

- نوع خودرو
- شماره شناسه یکتا
- ظرفیت باک سوخت بر حسب لیتر؛ عدد مثبت
- متوسط مصرف در 100 کیلومتر؛ عدد مثبت
- متوسط سرعت بر حسب km/h؛ عدد مثبت و دارای محدوده قابل تنظیم
- وضعیت آمادگی: `READY` یا `OUT_OF_SERVICE`

فیلدهای پیشنهادی: پلاک، توضیح، رنگ نمایشی، آیکن override، تاریخ آخرین سرویس.

قواعد:

- خودرو `OUT_OF_SERVICE` نمی‌تواند به مأموریت جدید منتشرشده تخصیص یابد.
- یک خودرو نباید مأموریت‌های زمانی هم‌پوشان داشته باشد؛ در MVP، بازه مأموریت از `startAt` تا `estimatedArrivalAt` است.
- تغییر سرعت پایه روی مأموریت‌های قبلی اثر ندارد؛ `speedSnapshotKmh` در مأموریت ذخیره می‌شود.
- برآورد سوخت مأموریت برابر `distanceKm × consumptionPer100Km / 100` است و فقط اطلاعاتی است، نه موجودی واقعی سوخت.

## 6. مرسوله

فیلدها:

- کد رهگیری یکتا و قابل تولید خودکار
- عنوان/شرح کوتاه
- نوع بار از catalog قابل مدیریت
- مبدأ انبار
- مقصد: یک گره سازمانی یا مختصات دلخواه به‌همراه عنوان مقصد
- وزن و حجم اختیاری با واحد مشخص
- توضیحات
- وضعیت چرخه عمر: `DRAFT`, `WAITING_FOR_DISPATCH`, `IN_TRANSIT`, `DELIVERED`, `CANCELLED`

قواعد:

- وضعیت `IN_TRANSIT` و `DELIVERED` می‌تواند از مأموریت فعال به‌شکل مشتق‌شده نمایش داده شود، اما تغییرات نهایی باید traceable باشد.
- یک مرسوله در یک لحظه فقط در یک مأموریت فعال قرار می‌گیرد؛ enforcement در سطح DB طبق ADR-019 (partial unique index روی `isActiveAssignment`).
- یک مأموریت می‌تواند یک یا چند مرسوله هم‌مبدأ و هم‌مقصد داشته باشد. در نسخه اول، UI باید ثبت تک‌مرسوله را ساده نگه دارد ولی مدل محدود نشود.

## 7. مسیر

مسیر یک asset قابل استفاده مجدد است و شامل نام، کد، نقاط مرتب، مبدأ/مقصد اختیاری، فاصله محاسبه‌شده و وضعیت فعال است.

روش‌های ایجاد:

1. import فایل CSV
2. کلیک/Tap متوالی روی نقشه
3. duplicate و ویرایش نسخه جدید

CSV نسخه اول:

```csv
sequence,latitude,longitude,label
1,35.6892,51.3890,مبدا
2,35.7219,51.3347,نقطه میانی
3,35.8400,50.9391,مقصد
```

قواعد اعتبارسنجی:

- UTF-8 یا UTF-8 BOM؛ header انگلیسی ثابت برای سازگاری فنی
- حداقل دو نقطه؛ sequence عدد صحیح مثبت و یکتا
- latitude بین -90 و 90؛ longitude بین -180 و 180
- ترتیب بر اساس sequence؛ نقاط تکراری متوالی reject یا با هشدار حذف شوند
- حداکثر تعداد نقاط و اندازه فایل از تنظیمات سرور خوانده شود؛ مقدار اولیه 10,000 نقطه و 5MB
- preview، تعداد نقاط، طول مسیر و خطاهای ردیفی پیش از ذخیره نمایش داده شود
- export CSV دقیقاً با همین schema انجام شود

## 8. مأموریت

فیلدهای اصلی:

- کد مأموریت یکتا
- خودرو
- انبار مبدأ
- مقصد سازمانی یا مقصد دلخواه با مختصات
- زمان شروع
- یک یا چند مرسوله
- نوع بار مشتق‌شده/قابل بررسی
- توضیحات
- مسیر اختیاری
- `speedSnapshotKmh`
- فاصله، زمان سفر و ETA محاسبه‌شده
- وضعیت persisted: `DRAFT`, `SCHEDULED`, `CANCELLED`, `ARCHIVED`

وضعیت نمایشی در زمان مشاهده به‌صورت derived است:

- قبل از شروع: `WAITING`
- از شروع تا قبل از ETA: `IN_PROGRESS`
- در ETA یا بعد از آن: `ARRIVED`
- مأموریت لغوشده: `CANCELLED`

قواعد:

- ایجاد از فرم مستقل و از workflow داخل نقشه ممکن باشد.
- انتشار مأموریت نیازمند خودرو READY، مختصات معتبر مبدأ/مقصد، زمان شروع معتبر، سرعت مثبت و حداقل یک مرسوله است.
- اگر مسیر وجود نداشته باشد، فاصله geodesic مستقیم و خط‌چین استفاده می‌شود.
- در صورت مسیر، مبدأ و مقصد مأموریت باید با ابتدا/انتهای مسیر در tolerance قابل تنظیم سازگار باشند؛ در غیر این صورت هشدار و تأیید صریح لازم است.
- طبق ADR-018: پیش از `startAt` مأموریت کاملاً قابل ویرایش است. پس از شروع (وضعیت نمایشی `IN_PROGRESS`/`ARRIVED`)، خودرو/مسیر/مبدأ/مقصد/زمان دیگر مستقیم ویرایش نمی‌شوند و تنها راه `cancel` با دلیل اجباری و سپس `duplicate` به مأموریت جایگزین است؛ فقط توضیحات/متادیتای غیرعملیاتی همچنان قابل ویرایش می‌ماند.

## 9. نمای نقشه

### اجزای ثابت

- نقشه اصلی
- نوار فیلتر
- جدول خلاصه مأموریت‌های جاری
- کنترل لایه/Provider (Provider می‌تواند حاصل رندر یک سبک Mapnik XML درون‌ریزی‌شده هم باشد؛ از نگاه نقشه سمت‌کاربر تفاوتی با هر Provider داخلی دیگر ندارد — پیشنهادی، ADR-022)
- سیکر زمان با حالت Live و Historical
- legend وضعیت‌ها و برچسب واضح «موقعیت‌ها تقریبی هستند»

### رفتار

- در حالت عادی فقط آیکن خودروهای مرتبط و marker دفاتر/انبارها نمایش داده شود.
- با انتخاب خودرو از نقشه، ردیف متناظر جدول select و scroll into view شود.
- با انتخاب ردیف جدول، marker select، map pan/zoom و کارت جزئیات باز شود.
- فقط برای مأموریت انتخاب‌شده مسیر، مبدأ و مقصد highlight شوند.
- مسیر واقعی تعریف‌شده solid و مسیر مستقیم fallback dashed باشد.
- Tap/click روی marker کارت جزئیات با مبدأ، مقصد، درصد پیشرفت، زمان باقی‌مانده، شروع، ETA، نوع خودرو، شناسه خودرو و نوع بار نشان دهد.
- clustering در تراکم بالا فعال شود؛ انتخاب cluster zoom کند.

### فیلترها

- مقصد
- مبدأ
- نوع خودرو
- وضعیت نمایشی
- زمان شروع قبل/بعد از مقدار انتخابی
- ETA قبل/بعد از مقدار انتخابی
- جست‌وجوی کد مأموریت، مرسوله یا شناسه خودرو
- «فقط مأموریت‌های فعال در زمان مشاهده»

فیلتر از context menu مبدأ/مقصد نیز قابل اعمال است. فیلترهای فعال به شکل chip نمایش داده و با یک action پاک شوند.

## 10. سیکر زمان

- حالت `LIVE`: زمان مشاهده از ساعت سرور/کلاینت با کنترل drift به‌روز شود.
- حالت `HISTORICAL`: کاربر زمان را جابه‌جا می‌کند و وضعیت تمام مأموریت‌ها برای آن زمان بازسازی می‌شود.
- کنترل‌های لازم: Live، play/pause، گام عقب/جلو، انتخاب تاریخ شمسی، نمایش ساعت دقیق و سرعت پخش اختیاری.
- بازه اولیه، 24 ساعت روز انتخاب‌شده است؛ امکان گسترش به بازه چندروزه با pagination داده وجود دارد.
- با ورود کاربر به Historical، badge واضح نمایش داده شود تا با داده جاری اشتباه نشود.
- بازگشت به Live یک action یک‌مرحله‌ای داشته باشد.

## 11. فرانمای وضعیت

کارت‌های اصلی:

- تعداد کل خودروهای تعریف‌شده
- تعداد خودروهای آماده
- تعداد کل مرسوله‌ها
- مرسوله‌های در انتظار ارسال
- مرسوله‌های در مسیر
- مرسوله‌های رسیده
- تعداد کل مأموریت‌ها
- مأموریت‌های در حال حرکت
- مأموریت‌های پایان‌یافته

بخش‌های تکمیلی نسخه اول:

- توزیع مأموریت بر اساس نوع خودرو
- مأموریت بر اساس مبدأ/مقصد پرتکرار
- مأموریت‌های شروع‌شونده در 24 ساعت آینده
- خودروهای خارج از سرویس
- هشدارهای تداخل مأموریت و داده ناقص

تمام KPIها باید تعریف دقیق، query واحد و timestamp آخرین محاسبه داشته باشند.

## 13. خارج از scope نسخه اول

- GPS/AVL واقعی، موبایل راننده و telemetry خودرو
- route optimization یا shortest-path آنلاین
- محاسبه ترافیک، آب‌وهوا، توقف و سرعت متغیر
- پرداخت، حسابداری، صدور بارنامه قانونی یا انبارداری کامل
- ارسال پیامک/پیام‌رسان
- multi-tenant SaaS عمومی

معماری نباید راه افزودن GPS واقعی را ببندد؛ ولی هیچ UI نباید داده تخمینی را واقعی جلوه دهد.
